## 2026-09-22 — своя телеметрия Mic Noize и причина дневных лимитов Cloudflare

- Лимиты на аккаунте выбирал не объём телеметрии, а рейт-лимитер воркера: `telemetry/worker/src/ratelimit.ts` в Moment Player делал `kv.put` на каждый запрос ingest/party/room, а бесплатный план даёт 1000 записей KV в сутки **на аккаунт**. Счётчики перенесены в изоляты воркера (окно 60 с, очистка после 10k ключей, тестовый сброс `resetRateLimits()`); записей в KV больше нет. Холодный старт сбрасывает окно — это защита от спама на уровне установки, а не глобальный лимит. Там же: `npm test` 91/91, `tsc --noEmit` чисто.
- Mic Noize получает отдельный воркер `micnoize-telemetry` со своей базой D1 и своим `/admin`, из того же исходника через `telemetry/worker/wrangler.micnoize.toml`. `ENDPOINT` в `ui/src/telemetry.rs` переключён на него. Квоты Cloudflare считаются по аккаунту, поэтому разделение даёт изоляцию данных и деплоев, а не дополнительные лимиты.
- В панели оператора приложения разделены не вкладками, а списком «Filter by application» (`all` / Moment Player / Mic Noize / legacy), и он показывается только на вкладках со здоровьем и инсталлами.
- Воркер задеплоен: база D1 `micnoize-telemetry` (c41e93a9…) создана, 13 миграций применены, `https://micnoize-telemetry.arkanoidvfx.workers.dev` отвечает, `/admin` отдаёт 302 на логин. Деплой без привязки Durable Object `ROOM` прошёл нормально: неиспользуемый экспорт класса wrangler не смущает. Оба воркера (Moment Player и Mic Noize) задеплоены с одного исходника.
- Найдена и закрыта дыра: пока секрет не выставлен, ingest принимал `X-Hmac: dev-mode` **в проде** — свежезадеплоенный воркер был открытым эндпоинтом (проверено живым запросом: 202). Теперь обход возможен только при `ENVIRONMENT` dev/test или запросе на localhost, а без секрета ответ 503 `ingest_not_configured` вместо 500 из WebCrypto. На Moment Player поведение не изменилось: секреты там выставлены, неподписанный запрос получает 401. Строка, записанная проверочным запросом, удалена — база `micnoize-telemetry` пуста (installs/sessions/events = 0).
- Осталось вручную: выставить четыре секрета нового воркера (`MICNOIZE_HMAC_SECRET` = `MNR_TELEMETRY_SECRET` из GitHub, `ADMIN_PASSWORD`, `ADMIN_TOKEN`, `ADMIN_SESSION_SECRET`) — `wrangler secret put` спрашивает значение интерактивно. До этого телеметрия и отчёты из релизной сборки будут получать 503.

## 2026-09-22 — любой микрофон по умолчанию, повтор установки драйвера и отправка логов

- Автовыбор микрофона работал только для устройств со словом `HyperX` в названии: на чужом ПК ничего не выбиралось и автозапуск молчал. `devices()` в `audio.cpp` теперь ставит первым микрофон связи по умолчанию Windows (`GetDefaultAudioEndpoint(eCapture,eCommunications)`), а контроллер без сохранённого устройства берёт HyperX, иначе первый в списке. Сохранённое устройство по-прежнему либо совпадает точно, либо остаётся невыбранным.
- В настройках, пока виртуального микрофона нет, показывается подпись и кнопка «Установить виртуальный микрофон»: отказ от UAC больше не требует перезапуска программы. Кнопка и подпись исчезают после успешной установки (`driver_ready`).
- Кнопка «Отправить логи разработчику» рядом с обновлениями: `telemetry::report` шлёт одним запросом заметку о текущем состоянии UI и хвосты (по 2 КБ) `results/tag-host.log`, `sessions.log`, `tag-headphones.log` как события `error` (`source: micnoize`). Они попадают в ту же панель оператора, что и ошибки Moment Player, и фильтруются по `app_id = mic_noize`; схема воркера не менялась. `send()` теперь отправляет пакет событий, а не одно.
- Проверки: release-сборка, строгий Clippy, Cargo test 28/28, `bin/bridge_check.exe`.
- Не проверялось: реальная доставка отчёта (локальная сборка собирается без `MNR_TELEMETRY_SECRET`, поэтому отправка в ней отключена по замыслу — проверять нужно на релизной сборке), внешний вид новых кнопок в живом окне (снимок UI не снимался, чтобы не останавливать работающий UI и TAG-хост), выбор микрофона на ПК без HyperX.

## 2026-09-22 — программа сама ставит TAG-драйвер на чистом ПК

- По отчёту с другого ПК: после установки `Setup.exe` UI показывал «Cannot start mic_tag_host.exe; run build.ps1», а затем `results/tag-host.log` дважды писал «TAG driver not found (run install-tag.ps1): HRESULT 0x80070490». Причина не в сборке: в поставку входят только `MicNoize.exe`, лицензия и заметки, а установить подписанный TAG-драйвер было нечем — `install-tag.ps1` не входит в пакет и требует `signtool.exe` из Windows SDK. У любого нового пользователя виртуальный микрофон не появлялся вообще.
- `components.rs`: `driver_installed()` читает узел устройства `HKLM\SYSTEM\CurrentControlSet\Enum\Root\ThinAudioGateway_4d699d4a 0` (без прав администратора), `install_driver()` запускает `wdmdrvmgr.exe -q -h <instance> -i <hardware id> <inf>` из скачанного core-компонента через `Start-Process -Verb RunAs` (полный путь к `powershell.exe` из `%SystemRoot%`). Тот же INF и те же идентификаторы, что у `install-tag.ps1`; настройки безопасности Windows не меняются, проверка подписей через SDK остаётся путём разработчика.
- Контроллер: драйвер ставится при старте, если core-компонент уже на месте, иначе сразу после его установки; на время установки автозапуск обработки ждёт, в шапке видно «Устанавливаем виртуальный микрофон: подтвердите запрос Windows…». Отказ от UAC показывает просьбу перезапустить и подтвердить — повторный запрос без рестарта не делается.
- `bridge.cpp` больше не зовёт `ensureTagHost()`, пока `bin/mic_tag_host.exe` не скачан (`tagHostInstalled()` в `tag_link.hpp`): гонка со стартом UI давала пользователю dev-текст про `build.ps1`. Обе оставшиеся ошибки TAG переведены на русский («Виртуальный аудиодрайвер не установлен», «Не удалось запустить фоновый процесс виртуального микрофона»).
- Проверки: Cargo test 28/28 с новым `driver_install_script_quotes_paths_with_spaces`, строгий Clippy, release-сборка UI, `bin/bridge_check.exe`. Кавычки аргументов проверены отдельно подставным процессом: Windows PowerShell не экранирует элементы `-ArgumentList` с пробелами, поэтому путь INF несёт собственные кавычки и доходит до программы одним аргументом (`%APPDATA%\Mic Noize\Components` содержит пробел).
- Не проверялось: реальная установка драйвера на чистом ПК и сам запрос UAC (на этой машине драйвер уже установлен, переустановка оборвала бы работающий TAG-хост), поведение при отказе от UAC, обновление `bin/MicNoize.exe` и выпуск нового `Setup.exe`. Вопрос о правах на распространение TAG demo эта правка не решает.

После сброса/опустошения очереди обнуляются регулятор дрейфа и выставленная частота выхода. Физическое отключение USB и принудительное опустошение очереди в этой проверке не воспроизводились.
- Выбор устройств, версии и запаса очереди сохраняется при изменении, без необходимости нажимать «Запустить». Отсутствующий сохранённый микрофон/выход больше не заменяется другим автоматически; требуется «Обновить» или явный выбор. Логика выбора покрыта `--self-test`.
- После underflow/сброса очереди TAG обнуляет накопленную коррекцию частоты: старое отклонение не переносится на заново заполненный буфер. Счётчик переданных кадров теперь 64-битный и не оборачивается примерно через сутки.
- `mic_check --lifecycle-tag 4`: успешно проверены ошибка отсутствующего входа без подмены микрофона, последующий нормальный запуск, 3 старта движка, 12 подключений клиента, чередование 48 кГц stereo / 44,1 кГц mono. Во всех muted-проходах выход строго нулевой; пропусков не зарегистрировано. Лог: `results/tag-lifecycle.log`. Это проверка жизненного цикла и отсутствующего endpoint, **не физическое извлечение USB-кабеля**. Появление endpoint в Windows асинхронно; тест ждёт его регистрации.
- Контролируемая подача речи/тишины 180 с: 18 000 блоков; p95 2,96 мс, p99 4,20 мс, максимум Run 8,33 мс; ни одного вызова свыше 10 мс. Результат: `results/afx-soak-180.json`. Проверяется SDK с записанной речью, не весь живой тракт. Прежние редкие паузы до 224 мс в этом прогоне не воспроизведены; их первопричина не доказана.
- После остановки/закрытия движка в `results/sessions.log` добавляется итог сеанса: UTC, режим, версия, запас, максимальные времена Run/Reset, пропуски и статус. Голос туда не записывается; файловые операции выполняются после завершения аудиопотоков. При аварийном завершении процесса итог может не сохраниться. Невозможность записать диагностический лог не препятствует остановке аудио.
- Финальная проверка пересобранного движка 15 с (`results/tag-final-smoke.log`): 1524 блока, максимум Run 8,29 мс, 0 underruns/drops/TAG gaps. Проверены mute/интенсивность и фактическая запись сводки в `sessions.log`.
- Для прослушивания: `results/listening-comparison/SDK_v2.wav` и `Broadcast.wav`. Это один прежний одновременный захват, примерно выровненный по задержке, с отдельным постоянным усилением для одинакового RMS. SDK-файл получен через прежний VB-CABLE, **не является новой записью TAG**. Метаданные в `comparison.json`; субъективное качество и подавление другого говорящего нельзя доказать одной корреляцией.

После исправления часов: минутный приём TAG с запасом 40 мс — 2 880 960 отсчётов, пик 0,53125, 0 ошибок драйвера и 0 опозданий хоста сверх 10 мс (максимальный интервал 2,96 мс). При этом зарегистрированы 1 underrun и 1 сброс очереди, максимальный вызов NVIDIA 103,72 мс. Это рабочий транспорт, но не подтверждённый стабильный режим: длительную паузу SDK текущий запас не покрывает. Логи: `results/tag-fixed-40ms.log`, `results/tag-receive-40ms.log`. Самопроверка `mic_check --self-test` дополнена сохранением часов при позднем пробуждении и проходит.

### Исследование драйвера

Проверка собственного виртуального микрофона и готового подписанного транспорта без VB-CABLE: [driver-feasibility.md](driver-feasibility.md). TAG demo установлен, отдельный C++-хост `mic_tag` собран и передаёт звук через API прямого буфера. Свой драйвер требует отдельного решения вопроса подписи.
