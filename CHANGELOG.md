## 2026-09-21 — проверка обновления 0.1.1 → 0.1.2 на этом ПК

Первая проверка полного пользовательского пути с опубликованными артефактами, без песочницы агентов (Setup и приложение запускал пользователь из Проводника; см. заметку о MSIX-виртуализации в `workflow.md`).

- `Mic-Noize-Setup-0.1.1.exe` скачан с GitHub, SHA-256 совпал с `checksums.sha256` релиза; на файл поставлен Mark-of-the-Web. Установка Velopack в `%LOCALAPPDATA%\MicNoiseReducer` за секунды: `current\`, `Update.exe`, `packages\`, ярлыки «Mic Noize» в меню Пуск и на рабочем столе, запись «Mic Noize» / Arkanoid VFX в «Приложениях». Показ SmartScreen пользователь не запомнил — не зафиксирован.
- 0.1.1 при первом запуске сразу нашла и скачала пакет 0.1.2 (6.2 МБ, через 5 с после установки) и параллельно скачала core runtime 1.15 ГБ, после чего показала ожидаемую ошибку «Архив компонента не содержит ожидаемый файл» (баг проверки пути в 0.1.1). Части остались в `Components\.download-rvc`.
- «Обновить сейчас» через ~2 минуты после установки: приложение вышло, `Update.exe` подменил `current\` на 0.1.2 и перезапустил его; `install-id.txt` и `settings.ini` сохранены; запись в «Приложениях» обновилась до 0.1.2.
- 0.1.2 установила core runtime за 7 с, переиспользовав скачанные части без повторной загрузки; временные каталоги удалены; маршрут стартовал сам (QuadCast → NVIDIA v2 → Thin Audio Gateway), голос слышен, `sessions.log`: 20 230 блоков, 0 underruns/drops, TAG gaps 0. Второй `mic_tag_host` не поднимался: установленное приложение работало с хостом из `bin` через существующий mapping.
- **Деинсталляция (`Update.exe --uninstall`) удаляет всю папку `%LOCALAPPDATA%\MicNoiseReducer`** — вместе с `settings.ini`, `install-id.txt` и `Components` (1.7 ГБ). Ярлыки и запись в «Приложениях» убраны, автозапуск хоста (`HKCU\…\Run`) не тронут. Следствие: у пользователя при удалении программы погибнут импортированные RVC-модели и настройки — данные надо отселить из корня установки (открытый пункт, код не менялся).
- Косметика: кнопка «Обновить сейчас» отрисована как активная и при «Установлена актуальная версия» (нажатие отключено).
- `Run.bat` не запускался из Проводника: в системном `PATH` этого ПК отсутствует `C:\Windows\System32\WindowsPowerShell1.0`. Теперь вызывает `powershell.exe` по полному пути и держит окно при ошибке. Dev-сборка после теста запущена из Проводника: настройки мигрировали в `%LOCALAPPDATA%\MicNoiseReducer\settings.ini`, runtime из `vendor` репо, хост прежний.
- Git: `main` = ветка Codex (fast-forward), приватный `origin` догнан, теги `v0.1.x` получены из публичного репо; процедура экспорта документирована. Не проверено: установка на чистом ПК, SmartScreen как таковой, обновление между двумя *будущими* версиями с delta-пакетом.

Ревью кода дало оценку 63/100 и семь пунктов; исправлены пп. 3–7 (пп. 1 — Git, 2 — Mute/Start/Stop снят пользователем). Репозиторий: `Arkanoidvfx/MicNoise`, ветка `main`; в Git только исходники, скрипты и документация.

До этого проверочные exe были старее движка. Baseline после правки: CTest 3/3, 14 Rust-тестов, Clippy чисто (`results/verify-step1.log`).
- `tag_host_autostart()` запускает `reg query` с `CREATE_NO_WINDOW` — раньше при каждом старте UI мигало консольное окно. `Run.bat` теперь вызывает `run.ps1` через `powershell -File`, а не открывает его.
- **Переподключение TAG.** Хост сбрасывает производителя через 50 мс без данных и заполняет паузу тишиной; раньше следующая запись клиента получала отказ и сессия падала с «restart processing». `TagClient::write` при первом отказе выбрасывает блок с накопленным долгом часов, заново регистрируется (`command(1)`) и возвращает `false`; `tagLoop` сбрасывает часы и приминг как при смене клиента. Два отказа подряд по-прежнему ошибка. Новые `Stats::tagReconnects` (в `sessions.log` поле `reconnects=`) и тест-хук `Engine::testStallMs`. Проверка `mic_check --tag-reconnect 2` с живым хостом: стойла 120 и 400 мс пережиты, `reconnects=1/2`, приёмник не терял поток (69–97 тыс. кадров на фазу), `TAG_gaps=0`, `underruns=0`, `drops=0`; разрывы захвата WASAPI (3 и 5) ожидаемы при паузе >20 мс. Регрессия `--persistent-tag 2` прошла. Логи: `results/tag-reconnect-check.log`, `results/persistent-tag-after-reconnect.log`. Первые ~50 мс дыры до срабатывания watchdog хоста никто не заполняет — одна короткая пауза вместо мёртвой сессии; стойло >2 с по-прежнему роняет сессию (watchdog микрофона). `HeadphoneClient` с порогом 2 с и авто-рестарт движка после ошибки не менялись.
- **Именованные константы C++.** `enum Hold` (`HoldBoost..HoldReverse`, `HoldPhrases`, `HoldLive`, `DiscordShift`, маски) и `enum Modified` в `hotkeys.hpp`; `PhraseEffect::State` с прежними числовыми значениями (ABI и Rust UI остаются числовыми). Вывод `effects_check` побайтно совпал с эталоном без полей времени (`results/effects-check-before-constants.norm.log`, `-after-`).
- **RVC: фиксированная задержка.** Три дефекта прежнего `RvcClient`: до первого ответа шёл сырой голос, затем та же речь преобразованной (дубль); каждый underrun навсегда добавлял 10 мс задержки; любой Discord-хоткей выключал RVC для своего голоса и требовал холодного рестарта. Теперь `RvcPlayout` — линия задержки `блок + 200 мс` (`rvcSlack`): входной отсчёт j слышен строго на j+D, опоздавшее отбрасывается, отсутствующее — **тишина, не сырой голос** (решение пользователя). Оба кольца тегируются поколением и выровнены по индексам; worker выдаёт ровно один выходной отсчёт на входной (нули при пропуске чанка, отставшего на ≥ 200 мс, и при ошибке сервера), после пропуска меняет stream id, чтобы сервер сбросил crossfade. Только DSP-поток подрезает `output_`. `rvc->process` перенесён до подмены источника Discord: pitch, фразы и повтор работают с преобразованным голосом, при Discord-удержании свой голос остаётся преобразованным. Mute = выключение RVC ⇒ после unmute D тишины. Проверки: `effects_check` (детерминированный тест playout: прогрев, точная задержка, частичный/полный underrun, отбрасывание опоздавшего без сдвига задержки, чужое поколение, сброс), `bridge_check`, `mic_check --rvc-check` с живым сайдкаром: 40 блоков точной тишины, затем 280/280 блоков преобразованы, 0 тихих; `rvc_check.py`: inference после прогрева 57–79 мс для блоков 100–500 мс, пики 75–244 мс (`results/rvc-playout-check.log`). Прослушивание человеком не проводилось. Зависший (не упавший) сервер даёт тишину с состоянием «пауза» до выключения; упавший UI выключает сам через ~250 мс.

### Прототип TAG и диагностика NVIDIA

TAG — проприетарная demo; условия постоянного использования пока не подтверждены. Начальный прогон с 20 мс дал пропуски; он не считается стабильным режимом. Первый речевой замер прервался из-за завершения тестового хоста по таймеру и не даёт достоверной задержки.

Контрольный A/B CUDA Graphs по 60 с (6000 блоков, `results/afx-comparison.json`): штатный режим p95/p99/max = 3,00/14,21/37,89 мс; Graphs = 5,27/15,02/29,77 мс. В обоих 127 вызовов длиннее 10 мс, ни одного длиннее 40 мс; PCM совпал побитно на этом входе. Устойчивого выигрыша Graphs не установлено, поэтому штатный режим сохранён. CPU-время `GetThreadTimes` имеет грубую дискретность и не позволяет надёжно отделить GPU-ожидание от вытеснения CPU. Без ETW нельзя приписать причину одному планировщику. Первые `afx-default.csv`/`afx-graphs.csv` использовали `sleep_until` с джиттером до периода системного таймера и не используются как финальное сравнение. Контрольные суммы всех 5 файлов из `nvidia-assets.sha256` совпали.

Повторный живой прогон (`results/tag-diagnostic2.log`, `tag-diagnostic2-receiver.log`): хост 120 с, приём 90 с / 4 320 480 отсчётов, 0 underruns/drops/ошибок TAG. Максимум Run 3,81 мс, Reset 0,65 мс. Это успешный короткий прогон, но не установление причины прежних редких пауз. Broadcast автоматически перезапустился через `NvBroadcast.Container.exe` после завершения процесса; прогон не считается тестом без Broadcast. Службы, автозапуск и системные настройки NVIDIA не менялись.

Проверка интегрированного движка `mic_check --smoke 4 TAG 60 2 40` (`results/tag-integrated-smoke.log`) прошла: 6067 блоков, 0 underruns/drops/TAG gaps, максимум Run 3,20 мс, Reset 0,22 мс, изменение интенсивности 0,011 мс. Проверены приём виртуального микрофона, смена интенсивности, mute/unmute, остановка и отказ второму TAG-хосту. Один capture discontinuity был при первоначальном запуске. Исходники, GUI и CLI собраны Release; UI использует тот же движок, визуальная автоматическая проверка окна в этой среде недоступна. Тест FPS/frametime пользователь отложил. Причина прежних редких пауз остаётся открытой; успешные короткие прогоны её не опровергают.

### Проверки надёжности и диагностика

- Перезапуск из трея: Release-сборка и Rust-тесты прошли; отдельный бит события не пересекается с Exit/завершением сеанса. Фактический клик по системному меню трея не автоматизирован.
- Иконка приложения: Release-сборка и Rust-тесты прошли; из собранного EXE успешно извлечён встроенный 32×32 кадр многоразмерного ICO. Iced декодирует встроенный RGBA PNG, а tray загружает малый кадр ресурса ID 1 с системным fallback.
- Доработка UI и индикации: Release-сборка и `--self-test` прошли. `results/ui-polish-lifecycle.log`: 12 подключений TAG, 3 старта движка, 48 кГц stereo / 44,1 кГц mono, восстановление после отсутствующего входа; 0 пропусков, muted-выход и его индикатор строго нулевые, остановка очищает состояние выхода. `results/ui-polish-cable.log`: 15 с, 1468 блоков, 725 760 принятых отсчётов, 0 underruns/drops, максимум обработки 3,16 мс. Голос не записывался; субъективное качество этими проверками не измерялось. Нативная визуальная автоматизация недоступна: внешний вид и восстановление значка после реального перезапуска Проводника не проверены автоматически.
- В резервном маршруте WASAPI добавлена проверка отсутствия пакетов микрофона в течение 2 секунд: события выхода больше не скрывают остановку захвата. После сброса/опустошения очереди обнуляются регулятор дрейфа и выставленная частота выхода. Физическое отключение USB и принудительное опустошение очереди в этой проверке не воспроизводились.
- Выбор устройств, версии и запаса очереди сохраняется при изменении, без необходимости нажимать «Запустить». Отсутствующий сохранённый микрофон/выход больше не заменяется другим автоматически; требуется «Обновить» или явный выбор. Логика выбора покрыта `--self-test`.
- После underflow/сброса очереди TAG обнуляет накопленную коррекцию частоты: старое отклонение не переносится на заново заполненный буфер. Счётчик переданных кадров теперь 64-битный и не оборачивается примерно через сутки.
- `mic_check --lifecycle-tag 4`: успешно проверены ошибка отсутствующего входа без подмены микрофона, последующий нормальный запуск, 3 старта движка, 12 подключений клиента, чередование 48 кГц stereo / 44,1 кГц mono. Во всех muted-проходах выход строго нулевой; пропусков не зарегистрировано. Лог: `results/tag-lifecycle.log`. Это проверка жизненного цикла и отсутствующего endpoint, **не физическое извлечение USB-кабеля**. Появление endpoint в Windows асинхронно; тест ждёт его регистрации.
- Контролируемая подача речи/тишины 180 с: 18 000 блоков; p95 2,96 мс, p99 4,20 мс, максимум Run 8,33 мс; ни одного вызова свыше 10 мс. Результат: `results/afx-soak-180.json`. Проверяется SDK с записанной речью, не весь живой тракт. Прежние редкие паузы до 224 мс в этом прогоне не воспроизведены; их первопричина не доказана.
- После остановки/закрытия движка в `results/sessions.log` добавляется итог сеанса: UTC, режим, версия, запас, максимальные времена Run/Reset, пропуски и статус. Голос туда не записывается; файловые операции выполняются после завершения аудиопотоков. При аварийном завершении процесса итог может не сохраниться. Невозможность записать диагностический лог не препятствует остановке аудио.
- Финальная проверка пересобранного движка 15 с (`results/tag-final-smoke.log`): 1524 блока, максимум Run 8,29 мс, 0 underruns/drops/TAG gaps. Проверены mute/интенсивность и фактическая запись сводки в `sessions.log`.
- Для прослушивания: `results/listening-comparison/SDK_v2.wav` и `Broadcast.wav`. Это один прежний одновременный захват, примерно выровненный по задержке, с отдельным постоянным усилением для одинакового RMS. SDK-файл получен через прежний VB-CABLE, **не является новой записью TAG**. Метаданные в `comparison.json`; субъективное качество и подавление другого говорящего нельзя доказать одной корреляцией.

После исправления часов: минутный приём TAG с запасом 40 мс — 2 880 960 отсчётов, пик 0,53125, 0 ошибок драйвера и 0 опозданий хоста сверх 10 мс (максимальный интервал 2,96 мс). При этом зарегистрированы 1 underrun и 1 сброс очереди, максимальный вызов NVIDIA 103,72 мс. Это рабочий транспорт, но не подтверждённый стабильный режим: длительную паузу SDK текущий запас не покрывает. Логи: `results/tag-fixed-40ms.log`, `results/tag-receive-40ms.log`. Самопроверка `mic_check --self-test` дополнена сохранением часов при позднем пробуждении и проходит.

### Исследование драйвера

Проверка собственного виртуального микрофона и готового подписанного транспорта без VB-CABLE: [driver-feasibility.md](driver-feasibility.md). TAG demo установлен, отдельный C++-хост `mic_tag` собран и передаёт звук через API прямого буфера. Свой драйвер требует отдельного решения вопроса подписи.
