# Виртуальный микрофон без VB-CABLE: проверка реализуемости
## Актуальное решение 2026-09-24: только общий WASAPI

Пользователь согласовал запрет монопольного захвата вместо поддержки одинакового усиления в обоих режимах. Хост build 2026092405 удерживает запрет exclusive только у подтверждённого Mic Noize endpoint; компенсация обычного режима сохранена. Функционально проверены отказ exclusive с AUDCLNT_E_EXCLUSIVE_MODE_NOT_ALLOWED, два shared-клиента, восстановление политики за 31 мс и shared-сигнал с ожидаемым пиком 0.1. Лог `results/tag-shared-install.log`, детали — CHANGELOG.

Прежний блокер паритета больше не относится к согласованному режиму работы. Ограничение самого драйвера осталось; это не новая версия драйвера и не поддержка exclusive. Реальная перезагрузка и сохранение политики/имени после неё ещё не проверены. Далее приведены исторические результаты исследования; перечни незавершённых работ ниже относятся к моменту соответствующей проверки.


## Проверка диапазона громкости 2026-09-24

Первый этап плана надёжности остановлен на проверяемом ограничении установленного подписанного TAG 2.0.0.1903 demo. Наличие команды в SDK не означает поддержку её текущим драйвером.

- Новый `mic_tag_probe` вызывает `TagPipe::ControlRequest(IoCtl_Line_SetVolumeControlParams, ...)` через поставляемый `tagapi.dll`. Запрос `Enabled=true, MinDb=-96, MaxDb=0, StepDb=1` вернул `0x80070001` (`ERROR_INVALID_FUNCTION`). Повтор с исходными параметрами вернул тот же код. `GetCommonData().Drv.FI.VolumeControlParams` до/после: `Enabled=false`, числовые поля 0. Изменения диапазона не произошло.
- Endpoint Windows сообщает диапазон от -96 до +30 дБ, шаг 1,5 дБ, master scalar 1, mute false, hardware support 0. Привязка через `IDeviceTopology` различает активную линию 1 и старую отключённую линию 3; одинаковые отображаемые имена не являются идентичностью.
- Синтетический синус 1 кГц с пиковой амплитудой `0.00316228`, переданный напрямую в постоянный хост, принят в shared с пиком `0.1`, RMS `0.0707107`, коэффициентом `31.6228`; exclusive — пик `0.00316228`, RMS `0.00223613`, коэффициент `1`. Дискретизация 48 кГц, два канала; измеренные discontinuities 0 в обоих прогонах. Первые 500 мс исключены. Shared получил 77 760 измеренных кадров, exclusive — 115 200. Физический микрофон не открывался, аудио на диск не сохранялось.
- Поэтому убирать текущую компенсацию -30 дБ нельзя: это усилит обычный захват. Сохранение компенсации оставляет exclusive тише; обещать нейтральный уровень в обоих режимах на этой схеме нельзя. Проверенные результаты относятся к текущей машине/драйверу, не ко всем версиям TAG.

Логи: `results/tag-volume-api-probe.log`, `results/tag-signal-shared.log`, `results/tag-signal-exclusive.log`; сводка — `results/tag-reliability-gate.md`. Повторяемые команды описаны в README. Во время проверки диапазона бинарники хоста/UI не заменялись; последующая локальная установка описана ниже.

**Последующая независимая реализация:** защита уровня перенесена в хост, endpoint выбирается через экземпляр драйвера и KS-топологию; опубликован отдельный снимок готовности без изменения audio v1. Проверены master/каналы/Mute с закрытым UI, готовность без слушателя, shared-сигнал, живой NVIDIA-тракт и восстановление производителя после задержек 120/400 мс. Новая пара host/UI установлена локально, прежняя сохранена. Логи `results/tag-control-*`, подробности в CHANGELOG.

**Не выполнено:** новая перезагрузка Windows, чистая установка, доказательство сохранения имени после загрузки; audio IPC с поколениями/номерами запросов, Планировщик, восстановление после падения при закрытом UI, ремонт и транзакционное обновление/откат. Публичного выпуска нет. Завершение плана требует решения ограничения диапазона на подписанном драйвере либо явно пересмотренного требования к shared/exclusive; автоматически заменять драйвер или отключать проверку подписей нельзя.

## Исходное исследование 2026-09-16

Проверено 2026-09-16. Это результат исследования и проверки пакета, а не установленная или измеренная реализация нового микрофона.

## Вывод

Собственный WaveRT-драйвер технически реализуем, но сейчас нет пути подписать его для обычной Windows 11: пользователь подтвердил отсутствие Hardware Developer Program и EV-сертификата. Обнаружен подходящий вариант для прототипа без собственной подписи — **Thin Audio Gateway (TAG) 2.0.0.1903 demo**, с готовым Microsoft-signed x64-драйвером и интерфейсом прямого доступа к буферу записи. Это сторонний проприетарный драйвер; условия постоянного использования и цена не установлены.

## Свой драйвер: что потребуется

- Microsoft SysVAD — исходная основа WDM/WaveRT, не готовый приёмник звука нашего приложения. В проверенной версии `97429c5623590d52f001249460daf43e6749d777` capture-путь `CMiniportWaveRTStream::WriteBytes` заполняет буфер через `m_ToneGenerator.GenerateSine`. Нужны собственный безопасный интерфейс передачи PCM, управление временем/буфером и обработка состояний клиента.
- NVIDIA SDK должен остаться в пользовательском процессе. В драйвер передаются только готовые PCM-отсчёты.
- Для подачи на подпись Microsoft нужны Hardware Developer Program и связанный EV-сертификат. Текущая регистрация предусматривает проверку организации/контактного лица. Локальная самоподпись не заменяет этот путь на обычной защищённой системе.
- Актуальная документация Microsoft описывает attestation как подписание для тестовых сценариев; это не Windows Certified. HLK/WHCP — отдельный путь сертификации. Нельзя представлять attestation как безусловную замену сертификации для публичного выпуска.
- В стандартном каталоге установленного Windows SDK 10.0.26100.0 есть SignTool, но проверенные WDK-компоненты `km/portcls.h`, `km/ntddk.h`, `km/x64/portcls.lib` и `WindowsDriver.Common.targets` отсутствуют. Для сборки своего драйвера потребуется WDK. Другие каталоги инструментов не проверялись.

Никакие параметры загрузки Windows, Secure Boot, HVCI или проверки подписи не изменялись.

В прочитанных документах не установлены все ограничения демоверсии, цена и права на постоянное использование/распространение. Из наличия скачивания не следует бессрочная бесплатная лицензия.

### Уровень виртуального микрофона (проверка 2026-09-22)

У текущего capture endpoint `GetVolumeRange` возвращает −96…+30 дБ, а `QueryHardwareSupport` — 0: Windows применяет программную регулировку. Поэтому системные 100 % усиливают PCM в общем режиме захвата. В заголовке TAG есть `IoCtl_Line_SetVolumeControlParams`, но установленный demo-драйвер отклонил попытки объявить фиксированные 0 дБ (диапазоны 0…0 и −1…0 дБ) с `HRESULT 0x80070001`. После обеих попыток исходный `mic_tag_host.exe` восстановлен; диапазон остался −96…+30 дБ. В коде приложения реализована компенсация этого усиления и удержание системного уровня на 100 % во время обработки; в релиз это не выпускалось. Эксклюзивный захват обходит программную громкость Windows и получит ослабленный PCM; он не покрыт этим решением. Для устранения самой системной крутилки нужен новый подписанный пакет драйвера: фиксированный аппаратный узел или настройки программного диапазона в INF (последнее документировано для Windows 11 24H2+). Возможность получить такой вариант у поставщика не проверялась.

### План прототипа

`QuadCast → WASAPI capture → неизменённый NVIDIA SDK → ограниченная очередь → TAG capture buffer → Discord`

1. Использовать только capture endpoint; выходной WASAPI render-поток и отдельная пара кабельных endpoints не нужны.
2. Наш C++-код обслуживает состояния клиента, формат, заполняет общий буфер готовым PCM и сообщает драйверу продвижение позиции. Планирование и запас очереди остаются под нашим контролем.
3. При сбое SDK передавать тишину/останавливать поток, без автоматической передачи необработанного микрофона.
4. Проверить запуск/остановку принимающего приложения, изменение формата, длительную стабильность часов и переподключение микрофона.
5. Измерить задержку тем же парным захватом QuadCast/виртуального микрофона и сравнить с Broadcast. Заявления автора о задержке транспорта не являются измерением нашего полного тракта.

## Другие проверенные варианты

- **VirtualDrivers/Virtual-Audio-Driver**: README содержит предупреждение о test signing и предлагает прямую интеграцию/shared memory как custom build по запросу. Наличие старого релиза с названием Signed не доказывает доступность нужного API в текущем подписанном пакете. Не выбран как готовая замена.
- **E2ESOFT VSC SDK**: есть SDK и демоверсия, но описанный на странице COM-интерфейс настройки не подтверждает прямую подачу в клиентский буфер без дополнительного транспорта. У trial указан шум на выходе. Для этой задачи TAG соответствует требуемой архитектуре точнее.
